## Funcionalidad incorporada: Auditoría (Fase 1)

- Nueva sección **Administración → Auditoría** (`/audit`), visible y accesible **solo para ADMIN**.
- API: `GET /api/audit/events` (listado paginado) y `GET /api/audit/events/:id` (detalle), con `@Roles('ADMIN')` a nivel de controlador.
- Consulta los eventos existentes de `audit.cambios`, que es la única fuente de eventos.
- Filtros por fechas (desde/hasta), usuario, entidad y acción; paginación `page`/`pageSize` con `meta { page, pageSize, total, totalPages }`.
- Detalle de cada evento como **campo / antes / después**.
- Entidades del filtro agrupadas visualmente por módulo (Empresas, Contactos, Usuarios, Automatizaciones); los encabezados no son seleccionables.
- Protección de datos: catálogo con **lista blanca** de tablas y columnas, exclusión de `password_hash` y de cualquier campo con aspecto de credencial, **sin JSONB crudo** en las respuestas, valores estructurados descartados y textos recortados a 500 caracteres.
- Consultas de solo lectura con parámetros enlazados; el módulo no escribe en la base de datos ni registra el contenido de las filas.
- Sin cambios en los triggers existentes de `audit.cambios`.

## Procedimiento de deployment

Comando oficial:

```powershell
.\scripts\deploy\Deploy-DaubertHub.ps1 -Deploy -AcknowledgeN8nAlreadyApplied
```

**Primer intento – falló sin afectar a PROD.** El build no pudo obtener los metadatos de las imágenes base (`node:24-alpine`, `nginx:alpine`) desde Docker Hub: `failed to fetch oauth token ... auth.docker.io/token: 504 Gateway Timeout`. El script terminó con `DEPLOYMENT FALLIDO` (código 5). Compose construye antes de recrear, así que **ningún contenedor de PROD se modificó**: `/api/health` siguió mostrando `1.0.4 / 1fe2063`, `api` healthy y `web` en ejecución. En ese intento el script ya había creado las anclas `rollback-1fe2063`.

**Diagnóstico de conectividad (solo lectura).** Desde Windows, el DNS y HTTPS hacia `auth.docker.io` funcionaban, pero Docker Desktop agotaba el tiempo (~30 s) al obtener tokens. La causa raíz **no se confirmó** (ver [Observaciones](#observaciones-técnicas-y-pendientes)).

**Segundo intento – correcto.** Según lo registrado por el operador: tras recuperar la capacidad de construir las imágenes, se retiraron de forma controlada las etiquetas `rollback-1fe2063` creadas por el primer intento, después de comprobar que coincidían exactamente con las imágenes en uso (el script no sobrescribe etiquetas existentes), y se ejecutó de nuevo el procedimiento oficial. Se construyeron las imágenes API y Web, se recrearon los contenedores y pasaron las verificaciones posteriores del script.

## Observaciones técnicas y pendientes

1. **Vulnerabilidades de dependencias (pendiente de análisis).** Durante `npm ci` se reportaron **4 vulnerabilidades** en las dependencias de producción de la API: **1 moderada, 2 altas y 1 crítica**. **No se analizaron sus causas ni se aplicó ninguna mitigación**, y no debe asumirse que estén corregidas. No se ejecutó `npm audit fix` ni se modificaron dependencias en este release.
2. **Advertencia de Vite.** El build de la Web avisa de chunks de más de 500 kB tras la minificación (el bundle principal ronda los 800 kB). Es una advertencia conocida; no se tomó acción.
3. **Prueba automatizada de integración con PostgreSQL (mejora pendiente).** Los tests del módulo de Auditoría usan un repositorio simulado; la consulta sobre `audit.cambios` se validó manualmente contra TEST, pero no existe una prueba de integración automatizada contra una base real.
4. **Ampliaciones futuras de auditoría (fuera del alcance de v1.0.5):** auditoría de folios (`operacion.series_documentales` y ajustes), de ejecuciones de automatización y de configuración de notificaciones de pago; eventos de inicio/cierre de sesión; y una política de **retención** de `audit.cambios` (hoy sin retención definida).
5. **Conectividad de Docker Desktop hacia Docker Hub.** Los registros del proxy interno de Docker Desktop muestran conexiones desde contenedores a `auth.docker.io` y `registry-1.docker.io` que se quedan ~30 s sin respuesta de forma intermitente desde el 2026-09-02. **La causa no se confirmó**; entre las hipótesis está la inspección de red del antivirus del equipo, sin probar. Conviene investigarlo antes del próximo deployment, porque puede repetir el fallo del primer intento.
6. **Anclas de rollback y reintentos.** Si un deployment falla después de crear las anclas, un reintento con el script aborta porque no sobrescribe etiquetas. Retirarlas a mano requiere confirmar antes que coinciden con las imágenes en uso.
