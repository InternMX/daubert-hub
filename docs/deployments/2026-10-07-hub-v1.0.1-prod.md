## Tratamiento de n8n

El delta `fbda7c6..0814e94` incluye archivos bajo `n8n/`: los exports versionados de workflows de Remisiones Audi y Remisiones Caterpillar, en los que solo cambió el segmento de usuario de Windows de las rutas, que pasó a `<WINDOWS_USER>`. No hay cambios de lógica, nodos, conexiones ni credenciales.

`Deploy-DaubertHub.ps1` bloquea por diseño cualquier release con cambios bajo `n8n/`. Para este release se usó `-AcknowledgeN8nAlreadyApplied`, que es una **confirmación explícita del operador** de que esos archivos corresponden a workflows **ya aplicados y verificados en PROD**: el script no lo comprueba.

- El switch solo levanta ese motivo de bloqueo y muestra una advertencia. **No** afecta a las migraciones ni a ninguna otra validación.
- El script **no importa, activa, desactiva ni modifica workflows de n8n**. Sus únicas mutaciones permitidas siguen siendo el etiquetado de las anclas de rollback y `docker compose up -d --build api web`.
- Los workflows que corren en PROD son los que están en la base de n8n, no estos archivos; n8n no se reinició ni se tocó.

Los exports versionados bajo `n8n/` conservan `<WINDOWS_USER>` en las rutas de Windows (ver [n8n/security-notes.md](../../n8n/security-notes.md)): **no son importables tal cual** y hay que restituir el usuario real del servidor antes de cualquier importación.

## Cambio en el gate de deployment (`0814e94`)

- Nuevo parámetro `-AcknowledgeN8nAlreadyApplied` en `Deploy-DaubertHub.ps1`.
- Sin el switch, un release con cambios bajo `n8n/` sigue **bloqueado**, con una razón que nombra el switch.
- Las migraciones siguen bloqueando siempre. Siguen bloqueando también las demás validaciones: candidato exactamente HEAD, árbol de trabajo limpio, health correcto, base de datos conectada, `environment` `PRODUCTION`, digests de imágenes, anclas de rollback e imágenes de Compose.
- Pruebas añadidas en `scripts/deploy/tests/Deploy-DaubertHub.Tests.ps1`. Documentado en [deployment-checklist](../operations/deployment-checklist.md).
